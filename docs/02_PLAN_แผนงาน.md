## 2. Contract กลาง v1 (เนื้อหาที่ต้องตกลงในประชุมแรก — เป็นการ "ออกแบบ" ไม่ใช่โค้ด)

แทนที่ placeholder ใน `ai-contract` ด้วยข้อมูลจริง ขึ้น version 0.2.0 แล้ว **freeze เป็น 1.0.0 ที่ M3** (§5)

### 2.1 ข้อมูลโจทย์มาตรฐาน (`Problem`) — ตัวกลางแทนไฟล์ xlsx
| ส่วน | ฟิลด์หลัก (ชื่อเสนอ) | หมายเหตุ |
|---|---|---|
| time | `days[]` (จ–ศ), `periods[]` (หมายเลข+เวลา), `lunchPeriods[]` (4,5,6), `maxPeriodByLevel` | ค่าจากกฎข้อ 1,2,18 อยู่ในนี้ ไม่ฝังในโค้ด |
| levels/groups | `groups[]`: `id`, `level` (ปวช.1…), `name` (ทค.1/1) | |
| courses | `courses[]`: `id`, `code`, `name`, `hours`, `kind` (theory/practice), `category` (general/dept/activity), `levelId`, `roomRequirement`, `fixedSlot` (วัน+คาบเริ่ม+คาบจบ หรือว่าง), `sharedGroups` (ทฤษฎีรวมกลุ่ม?) | `fixedSlot` มาจากข้อความ "จัดอยู่ในวัน…" |
| teachers | `teachers[]`: `id`, `name`, `position`, `minHours`, `maxHours`, `unavailable[]` (วัน+ช่วงคาบ), `eligibleCourses[]` (ถ้ามี) | `min/maxHours` มาจากตำแหน่ง |
| rooms | `rooms[]`: `id`, `type` (COM/LAB/แผนก/ภายนอก), `capacity`, `unavailable[]`, `shareable` | สามัญ = shareable |
| assumptions | `rules` (config: นับกิจกรรมเป็นชม.ครูหรือไม่, ฯลฯ — จาก Q1–Q12) | ทำให้เปลี่ยนการตีความได้โดยไม่แก้โค้ด |

### 2.2 ผลลัพธ์ตาราง (`Schedule`)
`assignments[]`: (`courseId`, `groupIds[]` — วิชาทฤษฎีรวมกลุ่มมีมากกว่า 1, `teacherId` — ว่างได้สำหรับวิชาสามัญ, `roomId`, `day`, `startPeriod`, `length`) · `lunch[]`: (`groupId`, `day`, `period`) — คาบพักกลางวันของแต่ละกลุ่มแต่ละวัน เป็น **ผลลัพธ์ของ solver** (FE ไม่เดา) — **รูปแบบเดียว** ที่ Solver, Validator, FE (การแสดง/แก้ไขมือ), และ Export ใช้ร่วมกัน

### 2.3 Endpoint
| Endpoint | หน้าที่ | ผลลัพธ์ |
|---|---|---|
| `GET /health` | สถานะ/เวอร์ชัน | |
| `POST /v1/import` | รับไฟล์ xlsx → `Problem` + **คำเตือน** (เช่น ห้องสลับ, ข้อความข้อกำหนดแปลไม่ได้) | FE ให้ผู้ใช้ตรวจ/แก้ก่อนยืนยัน |
| `POST /v1/solve` | รับ `Problem` + ตัวเลือก (seed, เวลาสูงสุด) → สร้าง job | `jobId` |
| `GET /v1/jobs/{id}` | สถานะ `queued / running / done / failed / cancelled` · ความคืบหน้า (`phase`, `percent`, `elapsedMs`) · **ประวัติค่าโทษต่อรอบ** (สำหรับกราฟข้อ 4.8) | `done` → `outcome` + `Schedule` + `Report` · `failed` → `error` |
| `POST /v1/jobs/{id}/cancel` | ยกเลิกงาน | |
| `POST /v1/validate` | รับ `Problem` + `Schedule` (จะมาจาก solver หรือผู้ใช้ลากแก้) | `Report` |

**กฎสถานะ job (ตัดสินแล้ว — ทุกเอกสารยึดตามนี้):**
- สถานะ: `queued → running → done | failed | cancelled`
- เมื่อ `done` ต้องมี `outcome`: `solved` (ผ่านกฎ Hard ทุกข้อ) · `partial` (ได้ตารางแต่ยังมีการฝ่าฝืน) · `infeasible` (จัดไม่ได้ — `Report.infeasibility[]` บอกสาเหตุ, `Schedule` ว่างหรือบางส่วน)
- `failed` ใช้เฉพาะความล้มเหลวของระบบ (`ALGO_ERROR`) — **การจัดไม่ได้ไม่ใช่ความล้มเหลว** (เป็นผลลัพธ์ที่ได้คะแนนข้อ 3.3)
- `POST /v1/import` ตอบ `Problem` + `warnings[]` (ดู §2.7) — ข้อความที่แปลไม่ได้เป็นคำเตือน ไม่ทำให้ import ล้ม

### 2.4 รายงาน (`Report`)
`violations[]`: (`rubricId` เช่น "1.8", `rule`, `severity`, `message`ภาษาไทย, `refs` ชี้ครู/ห้อง/กลุ่ม/คาบ) · `summary` ต่อข้อคะแนน (ผ่าน/ไม่ผ่าน/จำนวน) · `teacherLoad[]` · `infeasibility[]` (ถ้าจัดไม่ได้: **สาเหตุเป็นข้อๆ** เช่น "ปวช.1 ต้องการ 36 ชม. แต่ช่องว่างหลังล็อก = 35") · `metrics` (คะแนนโทษ, น้ำหนักที่ใช้)

### 2.5 รหัสข้อผิดพลาด (ที่ตกลงตอนนี้)
- **รหัส error ในสัญญา:** `INVALID_INPUT`, `ALGO_ERROR`, `NOT_READY`, `JOB_NOT_FOUND` — FE ตัดสินใจจาก `code` เท่านั้น
- `UNPARSEABLE_CELL` **ไม่ใช่ error** — เป็น `code` ของ `warnings[]` ตอน import (importer แปลข้อความเซลล์ไม่ได้)
- `INFEASIBLE` **ไม่ใช่ error** — เป็น `outcome` ของ job ที่ `done` (§2.3)
- **รหัสที่เกิดฝั่ง FE เท่านั้น (ไม่อยู่ในสัญญา):** `TIMEOUT`, `NETWORK`, `BAD_RESPONSE`

### 2.6 ชุดข้อมูลทดสอบร่วม (fixtures) — ทำเป็นไฟล์ใน `ai-contract/examples/`
| ชุด | เนื้อหา | ใช้ทำอะไร |
|---|---|---|
| **F1 sample** | ข้อมูลตัวอย่างจากไฟล์ xlsx ที่ได้รับ (แปลงเป็น `Problem`) | เคสหลัก |
| **F2 tiny** | 1 ชั้น 1 กลุ่ม 2 ครู | พัฒนา/debug เร็ว |
| **F3 infeasible** | ข้อกำหนดขัดกันโดยตั้งใจ (เช่น ล็อก 2 วิชาในกลุ่มเดียวเวลาเดียวกัน) | ทดสอบรายงานสาเหตุ (3.3) |
| **F4 variant** | ข้อมูลที่จำลองว่า "กรรมการเปลี่ยนโจทย์": ครูเพิ่ม/วิชาเปลี่ยน/ห้องเพิ่ม/ข้อจำกัดใหม่ | ทดสอบว่าไม่ฮาร์ดโค้ด |
| ผลเฉลยตัวอย่าง | `Schedule` ที่ผ่าน/ไม่ผ่านโดยตั้งใจ ต่ออย่างละกฎ | ทดสอบ Validator + FE stub |

### 2.7 ตัวอย่าง payload (ย่อ — ชื่อฟิลด์ตาม §2.1–2.5 · ค่าเป็นตัวอย่างจากไฟล์ xlsx บางส่วน)

## 3. กฎการทำงานร่วมกัน (Git + การสื่อสาร)

- **3 repo แยก** · `ai-contract` ดึงเข้าแต่ละ repo เป็นสำเนา `contract/` + ระบุเลขเวอร์ชันใน commit (ตามที่เขียนใน README ของ `ai-contract`)

- `main` ของแต่ละ repo ต้อง **รันได้และผ่านตัวตรวจ contract** เสมอ
- branch สั้น (≤ 1 วัน) · commit แบบ Conventional Commits · อ้างรหัสงาน (เช่น `A03`, `W3a`)
- ห้ามตกลงเปลี่ยน field ทางแชตอย่างเดียว ต้องมีไฟล์/PR
- **ใช้ AI ช่วยเขียนโค้ด:** ใช้ Task Brief (EPEF §17.3 · แม่แบบของฝั่ง FE: `06 §4`) ทีละงานขนาด XS–M · ไม่ให้ AI แตะ `contract/` เอง (C3) · ผู้ใช้เป็นคน review ทุกครั้ง

## 9. ซ้อมและวันแข่ง

**ก่อนวันแข่ง**
- [ ] ผ่าน M5; self-score ครบ; ซ้อมเต็ม ≥ 2 รอบ จับเวลา
- [ ] pin เวอร์ชันซอฟต์แวร์ทั้งหมด; ดาวน์โหลด dependency ล่วงหน้า (ห้ามพึ่งเน็ตสด)
- [ ] สคริปต์เริ่มระบบ 1 คำสั่ง + สคริปต์ตรวจ (`health` + import F1 + solve F2 + validate)
- [ ] ผลตารางสำเร็จของ F1 บันทึกไว้เป็น **โหมดสำรอง** (ใส่ป้ายบอกชัดว่าเป็นผลที่บันทึกไว้)
- [ ] สำรอง: โปรเจกต์ทั้ง 3 repo + ตัวติดตั้ง + ไฟล์ตัวอย่าง บน USB และ Drive
- [ ] เตรียมข้อมูล F4 ไว้ซ้อม "ถูกเปลี่ยนโจทย์"

**วันแข่ง**
1. ติดตั้ง/รันเครื่องเดียว → สคริปต์ตรวจ (≤ 10 นาที)
2. รับโจทย์กรรมการ → import → **อ่านคำเตือนทุกข้อ** → ปรับข้อสมมติถ้าจำเป็น
3. จัดตาราง → ตรวจด้วย Validator → ดูรายงาน; ถ้าจัดไม่ได้ ใช้รายงานสาเหตุ (นี่คือคะแนน ไม่ใช่ความล้มเหลว)
4. Export Excel/PDF เก็บไว้ทันทีทุกครั้งที่ได้ผลดี
5. Freeze ก่อนช่วงตัดสิน — ไม่อัปเกรด/ไม่เปลี่ยน contract
6. ระหว่างนำเสนอ: คนหนึ่งสาธิต (FE) อีกคนอธิบายเทคนิค (Algo) ตามสคริปต์ W10b
