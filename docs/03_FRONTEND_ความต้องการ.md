# 03 — Frontend: ความต้องการและสิ่งที่ต้องรองรับ (ยังไม่เกี่ยวกับหน้าตา)

> จุดประสงค์: รู้ให้ครบว่า FE "ต้องทำอะไรได้" และ "ต้องรองรับข้อมูลแบบไหน" ก่อนออกแบบ UI
> อ้างอิง: `01_EXPLANATION` (โจทย์) · `02_PLAN` (แผนรวม/contract) · รหัสคะแนน = ข้อในแบบประเมิน
> ลำดับความสำคัญ: **M** = ต้องมี (ผูกคะแนนโดยตรง) · **S** = ควรมี (ช่วยคะแนน/ลดความเสี่ยง) · **C** = ถ้ามีเวลา

---

## 1. ภาพรวมสิ่งที่ FE ต้องทำ (6 หน้าที่)

| # | หน้าที่ | ทำไมต้องมี |
|---|---|---|
| 1 | **รับข้อมูลเข้า** (ไฟล์ xlsx / โจทย์กรรมการ) และให้ผู้ใช้ตรวจ-แก้ก่อนใช้ | คะแนน 3.1 และความเสี่ยง "โจทย์เปลี่ยนตอนแข่ง" |
| 2 | **สั่งจัดตาราง** และดูความคืบหน้า | 3.2, 4.8 |
| 3 | **แสดงตาราง** หลายมุมมอง | 3.4, 2.2–2.4 |
| 4 | **แสดงรายงานการตรวจ/สาเหตุที่จัดไม่ได้** | 3.3 + ข้อ 1.x ที่ต้อง "ตรวจสอบได้" (ไม่งั้นได้ 0) |
| 5 | **ส่งออก** Excel / PDF | 3.5 |
| 6 | **นำเสนอ/สาธิต** | 5.1–5.2 และหมวด 4 (กราฟหลักฐาน) |

FE **ไม่ตีความกฎตารางสอนเอง** — ทุกการตัดสินถูก/ผิดมาจากรายงานของฝั่ง Algorithm; FE มีหน้าที่แสดงให้เห็นชัดและตรวจย้อนได้

## 3. สิ่งที่ FE ต้อง "รองรับในข้อมูล" (ต้องออกแบบโครงสร้างข้อมูลฝั่ง FE ให้ถูก)

| เรื่อง | ต้องรองรับ | เพราะ |
|---|---|---|
| จำนวนไม่ตายตัว | ชั้น/กลุ่ม/วิชา/ครู/ห้อง จำนวนเท่าไรก็ได้ | โจทย์กรรมการอาจมากกว่าตัวอย่าง |
| กริดเวลา | วัน/คาบ/คาบพัก มาจากข้อมูล (ปวช.1 ≤ 9, อื่น ≤ 11 คือกฎ ไม่ใช่ค่าตายตัวของ UI) | กฎเปลี่ยนได้ |
| รายการตาราง | หนึ่งช่องอาจมีหลายรายการ (2 กลุ่มเรียนพร้อมกันคนละวิชา) และวิชาหนึ่งกินหลายคาบ | วิชาปฏิบัติ 4–5 ชม., ทฤษฎีรวม 2 กลุ่ม |
| ความไม่สมบูรณ์ | ตาราง "ยังไม่ครบ/มีฝ่าฝืน" ต้องแสดงได้ ไม่ใช่เฉพาะตารางสมบูรณ์ | ตอนจัดไม่ได้ / ระหว่างแก้มือ |
| ข้อความ | ไทยล้วน ชื่อยาว ชื่อวิชาที่มีช่องว่างเกิน | ตัดคำ/ล้นช่องในตาราง |
| รหัสข้อผิดพลาดและผลของงาน | แยก error ตามสัญญา (`INVALID_INPUT` / `ALGO_ERROR` / `NOT_READY` / `JOB_NOT_FOUND`) กับข้อผิดพลาดฝั่ง FE (`TIMEOUT` / `NETWORK` / `BAD_RESPONSE`) · `UNPARSEABLE_CELL` คือคำเตือนตอน import · **`INFEASIBLE` ไม่ใช่ error แต่เป็น outcome ของ job ที่ `done`** (02 §2.3, §2.5) | ข้อความที่ผู้ใช้เห็นต่างกัน |
| เวอร์ชัน | แสดง/ตรวจเวอร์ชัน contract ที่ FE รองรับ เทียบกับของ algorithm | กันลืม sync |

## 4. ความต้องการที่ไม่ใช่ฟังก์ชัน (เฉพาะที่กระทบการออกแบบ)

| หมวด | ความต้องการ |
|---|---|
| ประสิทธิภาพ | แสดงตารางได้ลื่นเมื่อมีหลายสิบกลุ่ม/ครู; ไม่บล็อกหน้าจอระหว่างรอ algorithm |
| ความเสถียร | ไม่ crash เมื่อข้อมูลว่าง/ผิดรูป/เกินคาด (ทดสอบด้วยไฟล์เสีย) |
| ภาษา | ไทยทั้งหมด (ข้อความ error, หัวตาราง, ชื่อวัน, รายงาน) |
| ใช้งานได้ | ใช้คีย์บอร์ดได้ในส่วนหลัก; สี**ไม่ใช่ตัวบอกสถานะเพียงอย่างเดียว** (ผ่าน/ไม่ผ่านต้องมีข้อความ/สัญลักษณ์ด้วย) |
| เครื่องเดียวออฟไลน์ | ใช้งานได้โดยไม่พึ่งอินเทอร์เน็ตตอนแข่ง (ไม่โหลดฟอนต์/ไลบรารีจากเน็ต; ฟอนต์ไทยบรรจุในแอป) |

## 6. สิ่งที่ FE ไม่ต้องทำ (กันงานเกิน)
- ไม่มีระบบ login/สมาชิก/ฐานข้อมูลบนเซิร์ฟเวอร์ (โครงการแข่ง · DEBT-1)
- ไม่คำนวณ/ตีความกฎตารางสอนเอง (ให้ algorithm เป็นแหล่งความจริง)
- ไม่ทำ real-time หลายผู้ใช้ (ไม่มีความต้องการ)
- ไม่ทำ i18n หลายภาษา (ไทยอย่างเดียว)
- ไม่ทำแอปมือถือเนทีฟ (เว็บที่อ่านได้บนมือถือพอ)
