## 1. โจทย์คืออะไร (สรุป)

สร้าง **ระบบจัดตารางสอนอัตโนมัติ** ของแผนกช่างเทคนิคคอมพิวเตอร์ (ปวช.1–3, ชั้นละ 2 กลุ่ม, ครู 5 คน, ห้อง COM1–4 และ LAB1–2) ที่
1. **นำเข้าข้อมูล** (รายวิชา ครู ห้อง เวลา และ "โจทย์จากกรรมการ")
2. **จัดตารางเอง** ให้ผ่านกฎ 19 ข้อ
3. **ตรวจความขัดแย้ง + รายงานสาเหตุ** เมื่อจัดไม่ได้
4. **แสดงผล** ตามครู / ห้อง / นักเรียน / รายวิชา + หน้าเว็บให้นักเรียนดูตารางตัวเอง
5. **ส่งออก** Excel และ PDF
6. **อธิบายเทคนิค AI** ที่ใช้ และแสดงหลักฐานว่าลดความขัดแย้งได้จริง

> ข้อสำคัญที่สุด: ข้อมูลในไฟล์ xlsx น่าจะเป็น **ข้อมูลตัวอย่าง** แต่กรรมการจะให้ **"โจทย์จากกรรมการ"** อีกชุดตอนแข่ง (ข้อ 1.e ของแนวทางระบบ + คะแนน 3.1) → ระบบต้อง *นำเข้าข้อมูลแบบทั่วไปได้* ห้ามฮาร์ดโค้ดวิชา/ครูของไฟล์ตัวอย่างลงในอัลกอริทึม

## 5. วิเคราะห์ความเป็นไปได้ (ประเมินด้วยมือ ยังไม่ได้พิสูจน์ด้วยโปรแกรม)

- **ปวช.1 แน่นมาก:** ต้องเรียน 36 ชม. จากช่องที่มีได้ 40 (5 วัน × (9 คาบ − พัก 1)) และต้อง *เริ่มคาบ 1, ไม่มีช่องว่าง, ทุกวันมีเรียน, วิชาปฏิบัติ 4 ชม. เป็นก้อนเดียว* + วิชาสามัญล็อกวัน/คาบไว้แล้ว ลองจัดด้วยมือพบว่ามีทางจัด ~6 ก้อนปฏิบัติ (จ. บ่าย 1 · พ. 2 · พฤ. เช้า 1 · ศ. 2) แบบเกือบ "ทางเดียว" → เป็นกรณีทดสอบที่ดีสำหรับ solver
- **ภาระครู:** รวม 159 ชม. อยู่ในช่วงที่ทำได้ → *มีทางแบ่งครูได้แน่* แต่ต้องวางคู่กับเวลาว่างของครู A (พุธ 1–4)
- **ห้อง:** COM 4 ห้อง และ LAB 2 ห้อง ใช้พร้อมกันสูงสุด 6 กลุ่มปฏิบัติ → ความจุห้องน่าจะไม่ใช่คอขวดหลัก แต่ LAB มีแค่ 2 ห้องและมีวิชาที่ต้องใช้ LAB เฉพาะ (ปวช.1: 1001, 1002)
- **อาจ "จัดไม่ได้จริง"** เมื่อได้ข้อมูลของกรรมการ → ระบบต้อง **รายงานสาเหตุ** (คะแนน 3.3 และหมายเหตุท้ายแบบประเมิน: "ข้อกำหนดที่ขัดแย้งกันจนจัดไม่ได้จริง ให้พิจารณาจากหลักฐานการวิเคราะห์") → นี่เป็นฟีเจอร์ต้องทำ ไม่ใช่ของแถม

## 6. โจทย์นี้ในเชิง AI — เลือกเทคนิคอย่างไร

โจทย์คือ **Constraint Satisfaction / Optimization Problem (CSP/COP)** ตัวแปร = (วิชา, กลุ่ม) → (ครู, วัน, คาบเริ่ม, ห้อง) · ข้อจำกัด = กฎข้างบน · เป้าหมายรอง = คุณภาพ (เช่น กระจายภาระครูเท่าๆ กัน, ลดคาบเช้า/เย็นสุดโต่ง)

| เทคนิค | ข้อดี | ข้อเสีย | ตอบเกณฑ์ข้อ 4 (อธิบายได้/ใช้จริง) |
|---|---|---|---|
| **Backtracking + MRV/Forward-checking (CSP คลาสสิก)** | พิสูจน์ได้ว่า "ไม่มีคำตอบ" + ชี้สาเหตุได้ · อธิบายง่าย | อาจช้าถ้าไม่มี heuristic | ★★★ |
| **Local search (Min-Conflicts / Simulated Annealing / Tabu)** | ปรับปรุงเรื่อยๆ, แสดงกราฟ "ความขัดแย้งลดลง" (ข้อ 4.8) ได้ชัด | ไม่การันตีว่าครบ · ติด local optimum | ★★★ |
| **Hybrid:** CSP สร้างคำตอบเริ่มต้นตามกฎล็อก → local search ปรับคุณภาพ | ได้ทั้งความถูกต้องและกราฟพิสูจน์ | ซับซ้อนกว่านิด | ★★★ ← **แนะนำ** |
| **CP-SAT (OR-Tools)** | แก้ปัญหาแบบนี้ได้เก่งและเร็ว, พิสูจน์ infeasible ได้ | เป็น "กล่องดำ" — อธิบายหลักการ/ค่าตั้งต้น (4.2, 4.6) ยากกว่า, ต้องดูว่ากติกาอนุญาตไลบรารีหรือไม่ | ★★ |
| Genetic Algorithm | อธิบายง่าย ดูเป็น AI | ช้า/ยากที่จะได้ 0 ความขัดแย้งแน่นอน | ★★ |

**คำแนะนำ:** Hybrid (CSP + Local search) เขียนเอง เพราะแมปตรงกับข้อ 4.4 *Plan* (วิเคราะห์เงื่อนไข → ล็อกก่อน → จัดลำดับด้วย MRV) และ 4.5 *Act* (ดำเนินการจัด) และ 4.7–4.8 (ฟังก์ชันประเมิน + กราฟลดข้อขัดแย้ง) พอดี **CP-SAT ใช้เป็นตัวอ้างอิงตรวจคำตอบ/ตัวสำรอง** ได้ถ้ากติกาอนุญาต (UNKNOWN: ไลบรารีที่อนุญาต)

**ฟังก์ชันประเมิน (ต้องนิยามชัด — ข้อ 4.7):**
คะแนนโทษ = (จำนวนการฝ่าฝืน Hard × น้ำหนักใหญ่) + (ความไม่เท่ากันของภาระครู) + (จำนวนคาบสุดโต่ง/วันที่หนัก) … น้ำหนักเก็บใน config และอธิบายได้

## 7. คะแนนส่วน "ความสามารถของระบบ" (35) → ฟีเจอร์ที่ต้องมี

| 3.4 แสดงตาม ครู/ห้อง/นักเรียน/วิชา (2) | 4 มุมมอง + หน้าเว็บนักเรียน | FE |
| 3.5 ส่งออก Excel/PDF (2) | ปุ่ม export | FE (ฝั่ง client จากข้อมูลตาราง) |

**ตัวตรวจอิสระ (Validator)** เป็นไอเดียหลักของสถาปัตยกรรมนี้: รับ "ตารางใดๆ" แล้วตรวจกฎทีละข้อ ผูกกับเลขข้อในแบบประเมิน (1.1–1.12, 2.1–2.4) ใช้ 4 อย่าง: (1) พิสูจน์ต่อกรรมการ (ข้อ "ตรวจสอบได้") (2) ตรวจผลลัพธ์ของ solver เอง (3) ตรวจตารางที่ผู้ใช้ลากแก้ด้วยมือ (4) ให้คะแนนตัวเองล่วงหน้า

## 8. สถาปัตยกรรมและเส้นแบ่งความรับผิดชอบ

```
        ┌───────── เครื่องเดียววันแข่ง (localhost) ─────────┐
 xlsx ─►│ Frontend (คุณ)   ──HTTP+JSON──►  Algorithm API (เพื่อน)  │
        │  UI รีวิวข้อมูล / จัดตาราง / 4 มุมมอง /   • /import  xlsx→ข้อมูลมาตรฐาน+คำเตือน
        │  หน้านักเรียน / export / แสดงรายงาน     • /solve   สร้าง job + progress
        │                                          • /validate ตรวจตารางใดๆ ตามเลขข้อคะแนน
        └──────────── contract กลาง (ai-contract) ───────────┘
```

**เหตุผลของเส้นแบ่ง**
- **Algo เป็นเจ้าของ "ความหมายของข้อมูล"** (แปลง "จัดอยู่ในวันจันทร์คาบที่ 1-2" เป็นข้อมูลโครงสร้าง, กฎ, การตรวจ) → ถ้าโจทย์กรรมการเปลี่ยนรูปแบบ แก้จุดเดียวที่ importer
- **FE เป็นเจ้าของ "การมองเห็นและการนำเสนอ"** → คะแนนข้อ 3.4, 3.5 และ 5.2 (สาธิต) อยู่ที่ FE ทั้งหมด
- ทั้งสองฝั่งคุยกันผ่านข้อมูล JSON มาตรฐานเท่านั้น (ไม่ผูกกับรูปแบบ xlsx)

**ปรับจากแนวทางก่อนหน้า (ไฟล์ `reference/AI_COMPETITION_FE_ALGO_ARCHITECTURE.md` — ถูกแทนที่แล้ว)** เพราะตอนนี้รู้โดเมนแล้ว:
| ก่อนหน้า (สมมติ) | ตอนนี้ (รู้โจทย์) |
|---|---|
| ประมวลผล < 5 วิ, เรียกครั้งเดียวได้ผล | การจัดตารางเป็นการค้นหา → ใช้ **job แบบ async + ดูความคืบหน้า** (ได้กราฟความขัดแย้งลดลงมาโชว์ข้อ 4.8 ด้วย) |
| endpoint เดียว `/v1/process` | `/import`, `/solve` (+ ดูสถานะ), `/validate` |
| field เป็น placeholder | ใส่ของจริง (ดู `02_PLAN` §Contract) |
| ข้ามห้อง/ครู ไม่มีโดเมน | เพิ่ม "ชุดข้อมูลทดสอบ 4 แบบ" ในแชร์ (fixtures) |

## 9. ข้อควรรู้เชิงซื่อสัตย์
- ยังไม่ได้พิสูจน์ว่าข้อมูลตัวอย่าง "จัดได้" ด้วยโปรแกรม — การวิเคราะห์ใน §5 เป็นการประมาณด้วยมือ
- การตีความ Q1–Q12 เป็นของผู้เขียน ต้องยืนยันกับกรรมการ/ผู้จัดก่อนล็อก
- แบบประเมินนี้ให้ **คะแนนสาธิตจริง 6 + อธิบาย 4** (ข้อ 5) → ระบบที่ "แสดงให้เห็นได้" มีค่าเท่าๆ กับระบบที่ "จัดได้ถูก"
